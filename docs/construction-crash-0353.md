# 양측 0.3.52 건설 크래시 및 추적 누락 수정 (0.3.53)

## 덤프 증거

2026-11-01 21:26:01 / 21:26:07의 두 덤프는 simulation clock 11433에서
동일한 0xC0000005 / EIP 0x0040D941을 기록한다. ECX와 EDX가 0이며
`mov edx,[edx+394h]`에서 NULL을 참조한다. 네이티브 동기화 오류는 양측 0이다.
실행 파일과 HED/MFP의 SHA256도 양측이 같다.

스택의 직접 반환 주소는 0x4507D2, 그 위 호출자는 0x438BB5이다.
`worker construction -> 4505D0 footprint check -> 40DDF0 definition lookup ->
40D930 footprint reader` 경로다. 양측 요청 인자는 unit ID 172, target definition
0x0038, x=3251, y=2276이다. 0x0038의 정의 조회가 NULL을 반환했다.
이 주문을 최초로 생성한 상위 입력/AI 원인은 기존 덤프만으로 확정하지 않는다.

## 보호 경로

0x438B51에서 대상 faction/index/catalog/definition을 검사한다. 정의가 없을 때
발자국 정보를 임의로 만들거나 다른 건물을 대신 생성하지 않고, 원래의 건설 취소
경로 0x438C01로 이동한다. 이 검사는 해당 코드의 비용 처리와 footprint 접근보다 앞선다.
정상 정의는 원래 `mov ecx,esi; call 41F090`을 실행하고 0x438B58로 복귀한다.
카탈로그의 정상 포인터 값 자체가 변조된 경우까지 판별하는 메모리 무결성 검사는 아니다.

진단 전용 메모리에 최대 32개의 취소 기록을 남긴다. helper가
`invalid-build-targets.json`으로 저장하며 ID/type/owner/요청 대상/목적 좌표/주문 상태/
실패 이유/확정 명령 64바이트를 포함한다. 첫 거부 시 프레임 이력을 reason=2로 동결한다.
거부 이유: 1 faction 범위, 2 index 범위, 3 catalog 없음, 4 definition 없음.
게임 플레이어 데이터 변경은 원래의 건설 취소 코드가 수행한다.

## 0.3.51~0.3.52 추적 누락 원인

0x454464의 멀티플레이 분기는 0x454477에서 0x45448C로 직접 이동한다.
기존 추적 CALL이 있던 0x454487은 단일 플레이 쪽 경로이므로, 실제 멀티플레이에서는
추적기를 호출하지 않았다. 0.3.53은 공통 지점 0x45448C의 `mov eax,22260h`를
trampoline으로 연결해 원래 동작을 보존하고 추적기를 실행한다.

`sync-trace-status.json`은 이력이 비어 있어도 저장한다. 진단 활성화 여부,
분기 설치 여부, 호출 수, 완료 샘플 수, 현재 모드/clock으로 비수집 이유를 구분한다.
동결된 DAT/JSON은 `SyncTrace/g########-f##########/`에 한 번 보관해 같은 프로세스의
다음 경기에서 덮어쓰지 않게 한다. 모든 JSON/DAT는 기존 리포트 ZIP에 포함된다.

## 검증

- 제보 스택과 같은 unit/target/좌표로 원래 x86 경로의 0x40D941 오류 재현
  (주변 월드/본체 footprint 조회만 통제)
- 수정 후 원래 취소 경로의 반환/스택/주문 초기화 및 로그 값 검증
- 정상 정의의 원래 경로와 레지스터/플래그/스택/유닛 메모리 결과 비교
- faction/index/catalog/definition 실패 조합 검증
- 실제 멀티플레이 점프 분기와 단일 분기를 각각 실행해 공통 추적 지점 검증
- 원본/HD 정지 자식에 패치 설치, 원격 기록 읽기/파일 저장, 빈 이력 상태 저장,
  동결 이력 보관 검사
- 예외/정상 종료 helper 및 새 JSON/DAT의 리포트 ZIP 포함 검사

이 수정은 확인된 건설 NULL 접근 경로를 방지한다. 다른 Lost connection 원인과
실제 양측 장시간 전투에서의 재발 여부는 별도 검증 대상이다.
