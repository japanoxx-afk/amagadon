# 0.3.56 초기 DRAW 분석

대상은 제보 ZIP 20261102-003153/003112의 00:29 경기다. 양측 모두 0.3.54. 한쪽은 1024×768 HD, 반대쪽은 원본 800×600이다. 동일한 시뮬레이션 시계로 추적을 비교하면 clock 548까지 위치/체력 지문이 일치하고 clock 549에서 플레이어 2가 처음 다르다. clock 584에서 추적이 동결됐으며 원본 fingerprint mismatch가 증가했다. missingHistory=0, 로비 TCP 연결은 유지됐다. 따라서 이번 기록은 단순 접속 해제보다 전투 상태 불일치가 선행한다. 단, 누락 이력이 0이라는 사실만으로 모든 통신 오류를 배제할 수는 없다.

양측 최초 불일치 상세에서는 플레이어 2 일꾼 ID 138(type 18)의 좌표가 (163,1554)/(176,1541)로 다르고 나머지 해당 소유자 유닛의 표시된 위치·체력은 같다. 상세 캡처는 clock 592 부근이므로 정확히 clock 549에서 어떤 내부 명령이 달랐는지는 기록되지 않았다. CRT 난수는 이미 시작부터 다르지만 BGM/효과음 등 로컬 처리도 소비하므로 이를 원인으로 단정하지 않는다. 엔진 난수 인덱스는 최초 위치 차이 시점에 같다. 오류 카운터/판정 임계값을 완화하지 않았다.

코드 대조에서 HD의 0x408730(본진 자원 랠리의 정확한 대상 저장), 0x430e49(원본 이동 경로 설정 후 새 일꾼 채취 상태 지정)가 원본 실행의 RallySpawn에 빠져 있었다. 자원 랠리 사용 경기에서 서로 다른 시뮬레이션을 만들 수 있는 구체적인 차이다. 0.3.56은 HD에 이미 적용된 동일 어셈블리를 원본에도 연결한다. 이 차이가 이번 ID 138 분기의 유일한 원인임은 아직 입증하지 못했다.

scripts/build-rally-gather.py는 기존 probe-resolution.py의 두 해당 블록만 추출하고 실행 주소와 별도 데이터 테이블을 재배치하여 RallyGather.cs를 생성한다. 원본 Apply는 원본 바이트/해시를 확인한다. HD는 기존 구현을 유지한다. 코드는 실행/읽기 페이지, 1700×12바이트 대상 테이블은 별도 쓰기 페이지를 사용한다. 디스크 원본과 기존 HD 레시피는 변경하지 않는다.

scripts/test-rally-gather.py는 원본+새 후킹 및 배포 HD의 실제 코드를 각각 실행해 세 진영 본진, ore1/ore2 유형, 근접 검색, 비본진·비일꾼·다른 자원 제외 동작의 대상/명령/타이머 결과와 레지스터·플래그·스택을 비교한다. 유닛 분류 API 경계는 제어하며 실제 전체 경로 탐색 또는 두 PC 장기 전투 검증을 대신하지 않는다.

최초 불일치 유닛 목록에 orderTarget(0x414), orderState(0x464), orderTimer(0x478), rallyX/Y(0x1398/139c)를 추가한다. 운영 서버/게임은 재시작하거나 종료하지 않았다. 양측 새 런처로 게임을 다시 시작해야 적용된다.
