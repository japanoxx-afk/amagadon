# 리플레이 관전자 모드 정리와 멀티플레이 리플레이 설계 (0.3.70)

## 현재 리플레이 구조 (원본 EXE와 HD 패치 `.aghprob` 영역 확인)

- **기록**
  - 싱글플레이 경기 시작 시 HD 패치 코드(0x23350A0, 메일박스 0x233A000)가 다음 순서로 동작한다:
    1. 시작 상태 저장: 0x454BE0, kind 10/11
    2. 바로 다시 불러오기: 0x454CE0
  - 이후 매 틱 세 지점에서 런처와 이벤트로 동기화하며 기록한다:
    - kind 1: 키보드 버퍼 / 마우스 / 카메라
    - kind 2: 0x504D70 마우스 상태
    - kind 3: 0x45442F 최종 패킷 0x52F210 1408바이트와 명령 플래그(Format 3)
- **재생**
  - 메뉴(0x504F48==2)에서 저장본을 불러온 뒤, 같은 지점에서 기록값을 덮어쓴다.
  - 60프레임마다 유닛 상태 해시를 비교하고, 다르면 중단한다.
- **모든 경로가 `cmp [0x513ED4],1 / je` 로 멀티플레이를 건너뛴다.**
  - 멀티플레이 경기는 지금 기록되지 않는다.
  - 저장 후 재로드를 하는 이유는 기록 시작 상태와 재생 시작 상태를 같게 만들기 위해서다. 멀티플레이에서는 한쪽 PC만 재로드할 수 없다.

## 0.3.70에서 바꾼 것 (관전자 시점, Format 3 재생)

| 요구 | 원인 | 처리 |
|---|---|---|
| 안개 해제 | 화면·미니맵 시야 질의(observer_visibility, terrain_visibility)는 재생 중 0(보임)이었다. 하지만 world_resources 후크가 원래 시야값(2=미탐색)으로 다른 플레이어 유닛을 숨겼다. | world_resources도 재생 중에는 시야값 0을 쓴다. 실제 경기에서는 기존처럼 숨긴다(에뮬레이션 테스트). |
| 미니맵 클릭 | 재생 중 게임 입력은 기록값으로 덮이므로, 원본 미니맵 처리는 사용자 마우스를 보지 못한다. | 런처가 커서를 게임 좌표(1024×768, 화면 비율 유지 설정 반영)로 바꾼다. 원본 0x4080A0 규칙으로 미니맵 타일을 구한다: 사각형 0x4F9DD0, 배율 0x4F9DB8(0은 ½배, 1~2는 1배, 3 이상은 2배). 그 타일이 화면 중앙에 오도록 관전 카메라(0x5812E8/EC)를 옮긴다. 드래그도 따라간다. |
| 마우스 스크롤 | 기존 화면 가장자리 스크롤은 커서가 창 안에 있을 때만 동작했고, 휠은 처리하지 않았다. | 런처 프로세스에 저수준 마우스 후크를 둔다(게임에 주입하지 않음). 게임 창이 앞에 있을 때만 동작한다. 휠 한 칸에 3타일, Shift+휠·틸트는 가로. 가장자리 스크롤은 다른 모니터로 넘어간 커서도 인정한다. |
| 방향키 | 기존 유지 | |
| 종료 알림 | 재생 완료 시 상태줄 문구만 바뀌었다. | 완료 시 "리플레이 재생이 끝났습니다" 대화상자를 띄운다. |
| ESC 메뉴 | 재생 중 키보드는 기록값으로 덮여 게임 메뉴가 열리지 않는다. | ESC를 누르면 화면 오른쪽 위 HUD 텍스트(0x4A8720로 그리는 기존 자원 표시 영역)에 메뉴를 표시한다: Enter: 나가기, ESC: 계속, 현재 배속. Enter를 누르면 기존 중단 경로로 종료한다. |
| 1/2/4 배속 | 기존 구현(0x4D4C65 간격)을 유지 | 현재 배속을 HUD에 항상 표시해 동작 여부를 바로 확인할 수 있게 했다. |

**검증 범위**
- world_resources 후크: 설치된 x86 코드를 에뮬레이션(재생/실경기, 아군/적, 세 렌더 패스).
- 좌표 변환·미니맵 타일·카메라 범위·휠 누적: `ReplayTests.ObserverControls` 단위 검사. Mono에서 실행했고, Windows에서는 `--test-replay-process`에 포함된다.
- 실제 게임 화면에서의 클릭·휠·ESC·알림 확인은 Windows에서 해야 한다.

**제한**
- ESC 메뉴가 열려 있어도 재생은 계속된다.
  - 자식 프로세스는 응답을 10초(0x2710) 기다린 뒤 0xE001로 종료한다. 그래서 일시정지를 넣지 않았다.

## 멀티플레이 리플레이: 필요한 것과 실험 순서

동기화된 멀티플레이는 모든 PC가 같은 입력(플레이어별 최종 패킷)으로 같은 상태를 만든다. 따라서 다음 두 가지가 같으면 재생할 수 있다:
1. 같은 시작 상태
2. 매 틱 모든 슬롯의 패킷

**1. 매 틱 패킷 기록**
- 실경기에 런처 동기화 대기를 추가하면 렉이 생긴다. 이벤트 왕복 방식은 쓰지 않는다.
- 0.3.67부터 있는 sync-trace 링을 쓴다. 링은 1024틱, 틱당 2048바이트이고 다음을 담는다:
  - 최종 패킷 0x52F210 1408바이트
  - 엔진 난수, 유닛 해시
  - 숨은 상태
- 감시 스레드가 0.25초마다 새 슬롯만 읽어 파일에 이어 쓰면 비동기로 누락 없이 저장할 수 있다. 링은 30틱/초 기준 약 34초 분량이다.
- 게임을 멈추지 않는다.

**2. 시작 상태 (미해결 핵심)**
- (A) 경기 첫 틱에 원본 저장 함수(0x454BE0)로 저장만 하고 재로드하지 않는다. 저장/로드 왕복에서 빠지는 필드가 있으면, 재생이 첫 프레임부터 갈라질 수 있다. 싱글플레이에서 남아 있는 "AI 상태 불일치"와 같은 계열의 위험이다.
- (B) 저장본 없이 맵, 로비 슬롯, 종족, 팀, 시작 위치, 엔진 난수로 같은 경기를 다시 시작한다. 그 뒤 패킷만 주입한다.
- 어느 쪽이든 녹화 때의 유닛 해시(링에 이미 있음)와 프레임마다 비교하면 즉시 판정할 수 있다.

**3. 재생 실행 모드**
싱글플레이로 불러온 상태에서는 0x513ED4!=1 분기 때문에 멀티플레이 전용 처리가 빠진다:
- 패킷 선택 목록 적용(0x48BBDE)
- 플레이어별 0x4202A0(0x4544A5)
- 플레이어 형식(mgr+0x25138)이 사람이어야 AI가 개입하지 않는다.

이 분기를 재생 중에만 멀티플레이와 같게 돌리는 후크가 필요하다. 네트워크 교환(0x482CF0)은 재생기가 대신한다.

**4. 관전자 시점**
- 로컬 플레이어(0x4E7270)를 0(관전자)으로 두거나, 기록한 플레이어로 둔 채 시야만 해제한다.
- 0이면 HUD와 선택 처리에서 0번 플레이어 경로가 안전한지 확인해야 한다.

**Windows에서 할 실험 순서**
1. 같은 PC 두 인스턴스 경기에서 (A) 방식으로 저장하고 패킷을 기록한다.
2. 재생기로 불러와 1틱부터 유닛 해시를 비교한다.
3. 갈라지면 숨은 상태 기록으로 첫 차이 필드를 찾는다.
4. (A)가 안 되면 (B)를 시도한다.
5. 해시가 끝까지 같은 재생을 확보한 뒤 관전자 UI를 연결한다.
