# 내부 해상도 분석 / 0.3.3-preview

## 0.3.3: ore2 목표와 실제 리플레이 충돌 복원

Windows 충돌 덤프에서 0.3.2 리플레이가 첫 프레임 40d9b1에서 예전 unit+8 정의 주소를 읽어 접근 위반하는 것을 확인했습니다. 원본 44b5f7은 13e0바이트 유닛 구조체 전체를 읽어, 생성자가 초기화한 프로세스별 참조를 저장본의 주소로 덮습니다. 정의만 복원하면 이후 4bd413에서 unit+22c의 이전 스프라이트 주소가 다시 충돌했습니다.

관리 컨트롤러는 첫 재생 이벤트의 명령/그리기 전에 타입 상위 바이트에 따른 현재 카탈로그 5049fc..504a08을 사용해 unit+8을 복원합니다. 원본 446436..446522의 배열 배치를 따라 1cc 방향 프레임 17개, 210/218/220/228/22c/230 스프라이트, 234..254 프레임 9개의 기존 non-null 참조만 다시 연결합니다. 저장본에서 사용하지 않던 그리기 슬롯을 채우지 않도록 null과 기존 플래그를 보존합니다. 정의/그리기 참조 이외의 유닛 상태는 유지합니다. 단순히 해시 비교를 생략하거나 위치를 기록값으로 강제하지 않습니다. 게임이 비정상 종료하면 코드와 재생 프레임을 알립니다.

유닛 전체를 읽은 뒤에만 참조를 고치면 다음 유닛을 생성하는 중 이미 덮인 앞선 유닛을 참조할 수 있어, 추가로 44b5f7의 유닛 fread 호출에 24d00 wrapper를 둡니다. 생성자가 만든 최신 정의 및 1cc..254 참조를 스택에 보존하고 원래 fread를 호출한 직후, 저장본의 null 상태를 유지하며 각 유닛의 참조를 즉시 복원합니다. 원래 저장 상태의 위치/체력은 바꾸지 않습니다. 실패 반환과 원래 인수/보존 레지스터를 기계어로 검사합니다. 재생 전용 자체 자식의 메모리에서만 적용합니다.

반복 재생의 초기 AI 이동 및 명령 불일치를 확인했습니다. UI 처리 후의 마우스/선택 명령 재계산도 배제하기 위해 확정 명령을 사용합니다. 다음 프레임의 명령 블록 +64(52f250)가 직전 프레임의 UI 처리 후 확정된 64바이트 로컬 명령을 보존하므로, 이벤트 커서를 이동하지 않고 이를 읽습니다. 런처가 정지 상태로 생성한 자체 재생 자식에서만 검증된 454436의 원래 UI helper 호출을 전용 섹션 24e00 wrapper로 연결합니다. 원래 helper와 레지스터/플래그를 유지한 뒤 mailbox+200의 확정 명령을 로컬 플레이어 패킷에 복사하고 돌아옵니다. 원래 게임 파일은 바꾸지 않으며 실행 파일 해시와 원래 호출 바이트 및 빈 코드 공간을 확인하고 FlushInstructionCache 후 자식을 재개합니다. 마지막 프레임에 후속 블록이 없으면 현재 기록 패킷을 사용합니다. 이는 새로운 입력을 추측하거나 상태 해시 검사를 무시하는 방식이 아닙니다.

제보 파일 20261019-223423-30ea03d3.agr(0.3.2, 140개 초기 유닛, 4,182프레임)을 실제 게임 자식에서 완주한 경우에는 모든 기존 진행 틱 및 주기적인 유닛 위치/체력 해시 검사를 통과했습니다. 그러나 반복 시 AI 불일치가 남아 해당 파일의 완전 복구를 확인한 것은 아닙니다. 검증 자식은 스스로 종료했으며 다른 실행 중 게임을 제어하거나 종료하지 않았습니다. 0.3.2의 당시 출력 F1D57482…은 레시피 c1523655…를 별도 임베딩해 Armageddon.Replay032.exe로 생성합니다.

반복 검사에서 기존 Format 1은 완주와 AI 유닛 위치 불일치가 모두 재현되어 완전 호환으로 판정하지 않습니다. CRT rand(4bfff0)의 TLS +14 값 이외에 엔진은 4a3c50에서 581158의 인덱스와 4eac9c 테이블을 사용하며, 이 상태는 기존 기록에 없었습니다. Format 2는 이벤트 1/2/3 payload를 각각 2080/72/1416바이트로 확장하여 이 인덱스와 각 단계의 CRT 난수 값을 기록·복원합니다. 새 기록에는 적용하고 기존 파일을 임의의 추정 값으로 덮지 않습니다. 503bcc/cd/ce 스케줄러와 FPU 제어 값도 조사했지만 당시 재생 시작은 00/00/00 및 027F로 같아 이 값을 원인으로 단정하거나 강제로 바꾸지 않습니다.

독립 실제 게임 시나리오 검사는 원본 기록의 입력을 사용해 새 게임 패치에서 새 Format 2 파일을 생성하고 그것을 다시 검증합니다. 시나리오 생성에서는 원본의 상태 해시를 복구 성공으로 간주하지 않으며 원본 파일을 변경하지 않습니다. 일반 리플레이 경로는 계속 기록된 상태 해시를 확인합니다.

ore2는 원본 450a90이 클래스 2를 반환하는 type 303..305이며, 기존 패치의 300..302만 검사하는 조건에서 누락되었습니다. 이 여섯 종류를 포함하고 408730의 본진 우클릭 처리에서 이미 판정한 실제 자원 ID를 기억합니다. 전용 섹션 1b000..1ffb0에 1700×12바이트 목표 캐시(target+1, rallyX, rallyY)를 두며 기상 캐시 끝 1ac00 및 코드 시작 21000과 겹치지 않습니다. 생산 시 랠리 좌표와 활성 자원 종류를 검증해 원본 채굴 상태 2d를 적용합니다. 캐시가 없으면 기존 좌표 근접 탐색을 사용하고 다른 랠리 좌표에는 이전 목표를 쓰지 않습니다. 캐시는 저장 파일 형식을 변경하지 않으며 저장본/이전 리플레이는 당시 동작으로 재현합니다.

추가로 기존 430d88 훅은 원래 랠리 이동 경로 설정을 건너뛴 채 채굴 상태만 지정하는 문제가 있었습니다. 적용 위치를 430e49로 옮겨 원래 목적지 setter와 441c40 이동 설정을 수행한 뒤 채굴 상태를 지정합니다. 실제 원래 기계어의 목적지 setter를 실행하고 마지막 지도 경로 탐색만 제한된 stub으로 교체한 검사에서 이동 설정 선행·채굴 상태 유지·스택 규약을 확인했습니다.

현재 상태: 실제 새 Format 2 시나리오(4,182프레임)를 기록한 뒤 별도 게임 프로세스에서 재생해도 60프레임에 AI 위치 불일치가 재현됐습니다. 단계별 두 난수 계열의 전달 검사는 통과했지만 이것만으로 원인을 모두 해결하지 못했습니다. 리플레이 문제 해결 완료로 판정하거나 구형 파일의 완전 복구를 약속하지 않습니다. 테스트 시나리오는 원본 제보 파일과 구분해 .tools에 보관합니다.

검증: x86 30개 범주; 세 본진과 원본 채취 유닛 판정, ore1/ore2 여섯 종류, 47픽셀 떨어진 ore2 가장자리 클릭과 17픽셀 거리의 ore1 미끼, 변경된 랠리 캐시 무효화; Windows 네이티브 자식에서 오래된 정의/스프라이트 주소 복원 및 null 참조 보존, 확정 명령 lookahead의 커서 보존, 실제 x86 post-input wrapper의 플레이어별 복사 경계·스택·레지스터 보존. 실제 마우스로 새 게임을 조작해 장시간 채굴하는 시나리오와 멀티플레이는 미검증입니다.

## 0.3.2: 목록, 이벤트 동기화, 카메라와 랠리

사용자 런처 프로세스는 0.3.0이었으며 전역 단일 인스턴스 mutex가 새 0.3.1 창 실행을 조용히 무시했습니다. 버전별 mutex로 변경해 새 빌드를 실제로 실행할 수 있게 했습니다. 리플레이는 기록 시간/맵/프레임/버전 목록을 최신 파일 순으로 보여주고 더블클릭/Enter로 시작합니다. 시작 전에는 전체 아카이브와 게임 해시를 다시 검증합니다.

새 패치의 동기화는 런처에서 만든 자동 초기화 커널 이벤트 2개를 정지된 자체 게임 자식에 DuplicateHandle로 전달합니다. 메일박스 +40/+44는 요청/응답 이벤트 핸들입니다. 네이티브 notify는 SetEvent 및 WaitForSingleObject(10초), 런처는 이벤트를 기다린 후 원격 상태를 읽고 명령을 처리하며 응답합니다. 프레임당 3회 Sleep(1) 반복으로 Windows 타이머 단위가 누적되는 대기를 제거합니다. 원본 4295f0에서 가장 빠른 단계(index=4)의 대기는 이미 0이며 이 값을 임의로 더 낮추지 않았습니다. 실제 4d4c64/503c70 값과 동기화 방식을 로그에 남깁니다. FPS 향상률은 실제 게임에서 측정하지 않았습니다.

기존 0.3.0/0.3.1 출력 해시 77fcba1d… 기록은 compat/replay-0.3.0.json의 기존 레시피를 별도 임베딩해 Armageddon.Replay.exe로 재생합니다. 레시피와 완성 파일 해시를 모두 검증하고 새 HD 시험본은 바꾸지 않습니다. 당시 게임 시뮬레이션을 그대로 유지합니다. 이전 레코더의 polling에는 균형 잡힌 timeBeginPeriod/timeEndPeriod를 적용합니다.

카메라 세로 이동의 9개 상한과 최종 4a3d40 보정에서 mapHeight−24를 mapHeight−18로 바꿔 6타일 추가 하단 이동을 허용합니다. 실제 래스터와 안개는 32×24 유지하며 지도 밖 접근 방어를 적용합니다. 256 지도에서 maxY=238, 마지막 행의 화면 좌표는 y=544입니다.

생산 출구는 44cdf0의 원래 충돌/지형 탐색을 유지합니다. 44cf5b에서 호출자가 생산 함수 41f830의 반환 주소 41f97b인 경우에만 부모의 1398/139c 랠리와 14/18 위치 벡터로 첫 탐색 측면을 선택합니다. 다른 호출자는 보존합니다. 430d88에서 본진 type 0/100/200 및 원래 40a210이 판정한 채취 유닛에 한해 랠리 근처(각 축 32픽셀 이내)의 활성 ore type 300..302를 선택합니다. 원래 우클릭 채굴 경로 40959e의 target(+414), state=2d(+464), reset(+478)를 적용합니다. 별도 자원 생성이나 자원량 증가는 하지 않습니다. 추가적인 상태 테이블 없이 기존 저장된 랠리 좌표를 사용합니다.

검증: 기계어 26개 범주(커널 이벤트 성공/타임아웃, 네 방향 출구 초기값 및 호출자 보존, 원래 worker 분류 함수를 실행한 세 본진×유닛×자원 경계 조합), 독립 네이티브 자식의 실제 Windows 이벤트 왕복과 종료 경쟁 조건, 구버전 레시피 선택/재사용/변조 거부. 실제 전체 전투, 막힌 생산 건물의 최종 출구 선택, ore 도착 후 장시간 채굴, 멀티플레이는 미검증입니다. 새 시뮬레이션 변경을 포함하므로 서로 다른 버전 간 멀티플레이 동기화는 보장하지 않습니다.

## 0.3.1: 종료 경쟁 조건과 출력 여백

실제 사용자 기록에 5,073프레임의 완성된 기록이 있었습니다. 별도 네이티브 테스트 자식에서 제어 메모리를 PAGE_NOACCESS로 바꾸고 150ms 뒤 종료하도록 하여, 아직 프로세스 객체가 종료 신호를 보내지 않은 상태에서 ReadProcessMemory가 실패하는 상황을 재현했습니다. 이전 런처는 실패했고 새 런처는 종료 신호를 최대 500ms 기다려 정상 기록/재생 종료를 처리했습니다. 영구적인 오류에는 접근 주소/길이/Windows 오류를 남깁니다.

cnc-ddraw 동봉 설정의 설명에 따라 windowed=true/fullscreen=true/maintas=false/boxing=false를 사용합니다. GPU의 4:3 전용 표시 모드 전환 대신 현재 데스크톱 크기의 테두리 없는 창에 늘려 출력합니다. 레거시 설정은 ScreenProfile=1로 한 번 변환하고 그 뒤의 사용자 선택은 유지합니다. 실제 활성 프레임에서 4f75ec/4f75f0을 읽어 내부 해상도를 표시합니다. HD EXE 및 명령 형식은 변경하지 않아 0.3.0 기록을 유지합니다. 실제 게임 화면의 최종 출력 검증은 수행하지 않았습니다.

## 0.3.0: 명령 기반 리플레이 시험 기능

원본에 리플레이 메뉴나 기록 파일 형식을 확인하지 못해 런처와 별도 HD 시험본에 기록·재생 경로를 추가했습니다. 4532c7은 입력 갱신 후 프레임 시작, 453830은 마우스 상태 수집 후, 454429는 플레이어 명령 적용 전의 동기화 지점입니다. 단일 플레이 모드(513ed4 != 1)만 허용합니다. 자체 섹션 0x21000~0x25000에 코드를 두고 0x26000에 제어 메일박스를 둡니다. 실제 메일박스 VA는 0x233a000입니다. 원본 EXE를 변경하지 않습니다.

런처가 만든 정지 상태의 자식 프로세스에만 기록 모드를 설정합니다. 시작 시 454be0으로 별도 시작 저장본을 만들고 454ce0으로 다시 불러 동일한 재구성 경로를 거칩니다. 재생은 메뉴 상태 2에서 같은 저장본을 자동으로 불러옵니다. 프레임별 키보드 상태 2056바이트, CRT 스레드 난수 값, 카메라 원점, 이미 폴링한 키 이벤트, 마우스 상태 64바이트, 플레이어 명령/캐시 1408바이트를 기록·재주입합니다. 게임 진행 틱과 첫 프레임 및 60프레임마다 유닛 종류·소유자·좌표·체력의 해시를 비교합니다. 이는 모든 시뮬레이션 필드의 완전한 결정성을 증명하지는 않습니다. 상태나 처리 순서가 다르면 재생을 종료합니다.

동기화 대기는 유한하며 런처가 사라질 경우 기록은 비활성화하고 재생은 중단합니다. 정상 종료만 완성된 `.agr`로 묶고, 실패한 기록은 작업 폴더에 보존합니다. 재생에서 사용자 저장·불러오기를 차단하고 기록 중 수동 불러오기는 세션을 분리합니다. `.agr`에는 manifest.json/start.sav/commands.bin만 허용하며 크기, 해시, 이벤트 순서, 완료 상태, 저장 헤더 및 원래 게임 데이터/맵 해시를 검사합니다.

검증: 실제 삽입 x86 코드의 대기/복원/부트스트랩/파일 보호, 기존 HD 기계어 검증 포함 22개 범주; 관리 코드의 파일 왕복·변조·잘린 기록·경로 이탈·크기 제한; 별도 네이티브 테스트 자식의 시작 저장본·입력·난수·명령 전송, 동일 최종 좌표/체력, 의도한 상태 불일치 중단 및 명시적 취소. 테스트 자식은 게임 코드를 실행하지 않습니다. 실제 게임의 전투 시작→종료 및 저장 시나리오 재현은 아직 확인하지 않았습니다. 멀티플레이는 지원하지 않습니다.

이전 검사는 49efc0 툴팁 경로를 클릭 판정으로 잘못 분류했습니다. 실제 이벤트 함수 49f6c0과 실제 버튼 처리 함수 499e60을 함께 실행하여 x=920,y=645에서 버튼 눌림을 검증했습니다. HUD 실루엣 마스크는 (240,120)의 역변환을 사용하고 HUD 양옆은 게임 영역으로 판정합니다.

추가 검사 후 총 16개 기계어 검증 범주를 통과했습니다. 실제 수정된 전투 화면을 확인한 것은 아닙니다. 기존 시험본은 알려진 해시가 일치할 때에만 백업 후 교체하며 실행 중에는 교체하지 않습니다.

Armageddon.exe는 x86, 파일 버전 1.0.0.1, 게임 데이터 버전 1.15입니다.

## 검증 범위

실제 수정된 x86 명령을 Unicorn에서 실행했습니다. OS/COM 경계만 시험용 구현으로 대체했습니다. 타일 입력, 프레임버퍼 경계, 날씨 업데이트/래스터, 게임 난수 보존, 카메라 경계, HUD 그리기·툴팁·실제 클릭 이벤트, 자원·초상화 좌표, 유닛 표시 경계, 미니맵 투영과 경계 등 16개 범주를 통과했습니다.

0.2.0에서는 Windows 디버거로 별도 시험 설치를 30초 실행했습니다. 내부 1280×720, 소프트웨어와 DirectDraw pitch=1280을 확인했고 시작 단계에 예외는 기록되지 않았습니다. 시간 제한에서 시험 프로세스를 종료했습니다. 전투 검사가 아니며 0.2.1 수정본의 전투 실행 검사는 아직 하지 않았습니다.

런처 검사는 백업/복원, 설정, 필수 파일, 원본 및 레시피 변조 거부, 시험본 생성·재사용·제거와 원본 보존을 포함합니다.

남은 검증: 실제 화면과 입력, 모든 종족·지상/공중 유닛·건물·탄환/효과, 미니맵 클릭 이동, 전투 안개, 저장/불러오기, 사운드, 게임 속도, Alt+Tab/DPI/IME, ACE 편집/저장, 장시간 플레이·성능 측정·멀티플레이. 안정판 또는 크래시 예방 완료로 표시하지 않습니다.

ACE는 실행 전 기존 래퍼를 복원하는 처리를 유지합니다. ACE 내부 바이너리 안정성 패치는 아직 구현하지 않았습니다.
